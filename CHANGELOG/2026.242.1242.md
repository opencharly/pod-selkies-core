# 2026.242.1242 — fix: advance four stale pins off the bare-name candy chain

## Summary

Four pins in this candy reached tags that reference `pixi` and `plugin-record` by **bare name**.
Both became separate repos (`opencharly/layer-pixi`, `opencharly/plugin-record`) in the candy
cutover, so resolving those tags fails with `unknown candy`. Each producer had already fixed itself
in a later tag; this repo never picked any of them up.

```
pod-selkies                    v2026.240.2150 -> v2026.242.1235
layer-asciinema                v2026.237.455  -> v2026.240.0119
layer-wl-record-pixelflux      v2026.237.557  -> v2026.242.1239
layer-wl-screenshot-pixelflux  v2026.237.557  -> v2026.242.1239
```

**Both pixelflux layers are advanced to tags that themselves carry the new `pod-selkies`.** That is
deliberate rather than incidental: advancing only the direct `pod-selkies` pin leaves those two
layers still declaring `v2026.240.2150` (and the screenshot layer an even older `v2026.235.2110`),
which puts two versions of one candy in the graph:

```
Warning: candy github.com/opencharly/pod-selkies resolved to multiple versions;
         using newest 2026.242.1240 … ignoring 2026.184.2020
```

`PickCandyVersion` is the sole candy-version arbiter and picks newest project-wide, so resolution
would still be *correct* — but it would be charly's tie-break covering for a stale declaration.
This PR makes the graph declare one version. That is why the two pixelflux repos were fixed first
(`layer-wl-record-pixelflux#4`, `layer-wl-screenshot-pixelflux#3`, both merged and tagged) rather
than pinned around.

**The schema line and the CI charly pin move as one atomic change with the rest.**
`charly box validate` refuses to run until the schema is migrated:

```
schema 2026.240.1943 is required (found "2026.232.0520"). Run: charly migrate
```

and the migration is exactly what makes the CI's pinned charly too old:

```
config schema 2026.240.1943 is newer than this charly supports
```

Landing either half alone leaves the repo broken in one direction or the other.

**Breaking change + rollback:** none — every pin advances onto a published tag whose difference is

part re-creates either the `unknown candy` errors or the schema/CI mismatch.

**Producer → consumer order:** satisfied — all four candy tags and charly `v2026.241.1130` are
merged, tagged and published.

### 3. Why `CHARLY_PLUGIN_ONLY=1` — RCA, not a dismissal

Run without it, this gate emits one warning, and it is charly's own deliberate signal, so it gets a
root cause. `plugin_loader.go:434 warnSkippedFHSPlugins()` fires when the running binary is not at
`/usr/bin`/`/usr/local/bin` **and** `/usr/lib/charly/plugins` holds `.providers` manifests. Its own
comment states the intent: those plugins *"were built against a different charly version (issue
#328)"*, so a dev binary must not load them, and the warning makes the skip visible instead of
silent.

```
(a) What would have been loaded:  /usr/bin/charly version -> 2026.187.2228
    …against a tree requiring schema 2026.240.1943 — 55 days and a schema epoch apart.
    Refusing to load them is CORRECT; loading them would be the defect.

(b) Caused by this PR? No — it fires identically on an untouched clone of main.

(c) Does the skip weaken this gate? Provably not. plugin_loader.go:454 documents
    CHARLY_PLUGIN_ONLY=1 as "the supported way to resolve AS-IF-UNPACKAGED" — it DROPS
    the FHS path from the search, masking nothing, and its output is byte-identical to
    the normal run minus that one line.
```
