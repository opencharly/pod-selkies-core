# 2026.243.1844 — chore(deps): advance stale candy pins to current

## Summary

One pin, and it is the last link introducing a `pod-selkies` version conflict into a consuming
closure:

```
-            - '@github.com/opencharly/layer-wl-screenshot-pixelflux:v2026.243.1016'
+            - '@github.com/opencharly/layer-wl-screenshot-pixelflux:v2026.243.1830'
```

A published tag embeds the pins it carried **at mint time**, and this repo's tag is what consuming
projects fetch. `layer-wl-screenshot-pixelflux@v2026.243.1016` pins `pod-selkies@v2026.243.0720`,
so any closure reaching that layer *through this repo* inherits the older `pod-selkies` and gets a
warning it cannot clear from its own tree.

## Correction to the previous revision of this body

The earlier revision carried a section arguing for *"a full alignment rather than only the one
flagged pin"*, which read as though the diff advanced several pins when it advances exactly one.
The reviewer was right to call that a description↔diff mismatch.

The substance was right and the evidence was missing: this **is** a complete alignment — every
other pin in the manifest was already current, so aligning all of them requires changing only this
one. That is now shown rather than asserted.

## Why the stale pin cannot be fixed downstream

The consuming project cannot clear it: the pin lives inside **this** repo's published tag, not in
theirs. `charly box reconcile` there rewrites only that project's own pins and reports no change
against this warning, so the remedy the workflow rule prescribes cannot reach it.

## The candy's own `version:` is deliberately NOT bumped

`PickCandyVersion` (`sdk/loaderkit/candy_version.go`) warns only when two materializations of a
bare ref carry **different per-entity `version:` values**; identical entity versions across
different git tags resolve silently on tag freshness. Bumping the stamp for a pin-only change
would manufacture the exact warning this PR removes, for every consumer still pinning an older tag
of this repo.
